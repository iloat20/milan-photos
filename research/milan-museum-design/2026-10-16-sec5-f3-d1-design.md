## 1. 现状与证据

- 序厅 = `photos.slice(0, HERO_MAX)`（`app.js` `renderHeroCarousel`），即**陈列序**前 8 张。当前前 8 恰含 360×360 的《夜泊》（第 5 席），且 5 张 1024 档作品坐拥首屏。
- 陈列序 = `manifest_order_key`（date 倒序、同日文件名倒序）——环境无关、不随 mtime 漂移；补齐 featured 不影响该序（序厅选片与陈列序解耦）。
- 卡片画心 `.card-media img` 是 `width/height:100%`（会随格宽 / 重点陈列放大）；灯箱与序厅 `img` 是 `width:auto` + max 约束（**原生尺寸封顶**）。故「放大发虚」的实际暴露面 = 卡片（格宽 260–430px、重点陈列行可到 ~640px+、未来重排后《夜泊》若落到 `is-feature` 更明显）。
- 序厅首图预载有**两处**：`index.html` 解析期内联脚本（读 `data.photos[0]`）与 `app.js` 的运行时兜底（`folderPhotos[0]`）。F-3 改变首张后两处都必须跟着「策展首张」走，否则白拉一张高优先级图。
- CSP：内联脚本内容变化 → 构建期自动重算 hash（`tools/csp.mjs`），无人工动作；产物四件套（index.html/app.js/styles.css/manifest.json）任一变化 → SW 版本指纹自动更新。

## 2. 设计

### 2.1 F-3 机制（featured → manifest → 序厅/预载）

```
photos/meta.json  "featured": 1..N（唯一正整数）
        │ sync（photos_lib.photo_item 校验 + 归一；sync_photos 写顶层 hero 指针）
        ▼
photos/manifest.json  photos[].featured（序厅选片） + hero: "<file>"（= featured 最小者；缺省 photos[0].file）
        │
        ├─ app.js   selectHeroPhotos(photos, HERO_MAX)：有 featured → 按 rank 升序全量；无 → slice(0, HERO_MAX)
        │           （HERO_MAX 移入 src/util.js，只此一处定义）
        └─ index.html 解析期预载：只查 hero 指针（`list.find(p => p.file === data.hero) || list[0]`），不重算规则
```

- **校验（sync 端）**：`featured` 缺省 = 不参选；出现即须为非 bool 正整数且**全局唯一**，否则 `SystemExit` 报错退出（含文件名 / 冲突名）。与 slug 同哲学：策展笔误在生成端大声红，不静默兜底。
- **平级行为（JS 端防御）**：若拿到手工改过的清单（排名重复），`Array.prototype.sort` 稳定 → 保持陈列序，行为确定。
- **一致性钉点**：`manifest.hero === selectHeroPhotos(manifest.photos, HERO_MAX)[0].file` 由 `tests/unit/util.test.mjs` 的「真清单契约」逐条断言（python 端选择规则 ↔ JS 端选择规则 的漂移即红）。
- **降级路径**：旧清单（无 featured / 无 hero）→ app.js 回落 `slice(0,8)`、内联脚本回落 `photos[0]` —— 行为与 F-3 前完全一致。

### 2.2 D-1 机制（低分辨率钳制）

- `LOW_RES_MAX_EDGE = 640`（`src/util.js`）；`lowResCapWidth(photo)`：宽高任一缺失 → 0（不钳）；`min(width,height) > 640` → 0；否则 → `width`（源宽）。
- 卡片装配：cap > 0 时给 `.card-media` 加 `is-lowres` 类 + 行内 `--card-maxw: <w>px`；CSS：

  ```css
  .card-media.is-lowres { max-width: min(100%, var(--card-maxw, 100%)); margin-inline: auto; }
  ```

  即：宽格 / 重点陈列行里画心不再拉满，居中显示为「小尺幅原作」；窄于源宽的格保持 100%（只防放大、不禁缩小）。
- 灯箱：`lightboxNeed` 的 `min(scale,1)` 已是「小图不放大」；不改。缩放倍率不按图降级（决策见 §0）。

- **R1 单测**：测试先行后 `npm run test:unit` → `SyntaxError: The requested module '../../src/util.js' does not provide an export named 'HERO_MAX'`，util.test.mjs 整文件红（node:test 独立进程，其余文件不受累）。

- **R3 D-1 首版用例即暴露测法问题**：按 500px 视口断言「格宽 > 380」时实测**格宽仅 224px** —— 移动端两列、桌面 auto-fill 的座面格宽常态在 170–330px，永远到不了源宽 360；放大症状只可能出现在「重点陈列」行。用例改为在 DOM 上重现 `is-feature` 行状态再量；复验红态（临时摘掉 CSS 钳制）：`重点陈列行里画心仍不得超源宽` 失败，`Received: 460.796875`（恰为 64vh × fit），而摘除钳制前常态格宽断言 `before ≤ 361` 仍过 —— 证明强护栏正是重点陈列行那一条。
